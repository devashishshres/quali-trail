# Employer review portal: design and handoff

Status: built on `feature/employer-review` behind `EMPLOYER_REVIEW_ENABLED` (off by default). Not applied to any hosted
database, not deployed, no real email sent. Revision 2 narrows what can be shared (below). Coordinate with the open
bug-fix work before release.

## Intent

A technician shares records they choose with **one** employer-reviewer email address. Only two kinds of item can be shared:

1. **Confirmed work**: a job with at least one confirmation the confirmer allowed to be shared outside QualiTrail. Shows
   the job title, type, date and what was confirmed. The supervisor's name appears only if they separately allowed it.
2. **Uploaded certifications**: title, issuer as recorded, dates and verification status. The original file is shared only
   if the technician separately ticks it for that certificate (off by default).

The reviewer proves they control that address by signing in with it (confirmed email) and sees a read-only, immutable,
expiring, revocable packet. That proves control of an inbox and nothing more: it is never described as verified identity,
employment or authority.

No job import, matching run or report is needed to share.

## Non-goals and anti-goals

Never shared: job-fit reports, requirements, AI explanations, unconfirmed work, training and other record types, work
documents (originals), free-text summaries, equipment/skill lists, credential numbers, profile details other than name and
trade, supervisor or customer comments, signatures, email addresses and customer names or contact details.

No candidate search, messaging, hiring decisions, automatic applications or contacting verifiers. No broad employer access
to worker tables. No change to TinyFish, matching results, verification statuses, the worker sign-up policy or live
feature settings. No retroactive consent: confirmations given before this feature (or without ticking the box) stay
private and are counted as "withheld" in the technician's picker, with an honest explanation.

## Approaches considered

1. **Frozen packet copy, account-based recipient (chosen).** At share time the server builds the packet from the
   technician's own data and stores it immutably with a SHA-256 hash. The reviewer signs in with the invited address.
   Mirrors the supervisor-invitation pattern already in the codebase, so a forwarded link cannot open the packet for any
   other account and nothing in the reviewer's session can reach worker tables.
2. Live view over worker tables with a scoped grant. Rejected: needs new RLS paths for employers and the packet would
   change under the reviewer.
3. Email one-time code without an account (the customer sign-off pattern). Rejected: a forwarded link must not grant
   access to a different account, and an account gives a stable list of received packets and clean revocation.

## How it works

- **Database** (`supabase/migrations/20261120100000_employer_review.sql`, additive): `employer_shares` (frozen packet,
  hash, shared record ids/kinds/versions/file hashes and per-certificate original flag, invited address until used, token
  hash, status, reviewer account, expiry), `employer_share_events` (append-only: invited, accepted, viewed,
  original_opened, revoked, expired; never tokens or URLs), `review_share_consents` (insert-only: share permission plus a
  separate show-name flag) and `signoff_share_consents` (insert-only: a customer's separate permission). RLS on, all client privileges revoked; only service-role functions touch them, each checking
  the caller. Email-delivery checks are replaced by supersets adding the new kind and related type.
- **Eligibility is decided in the database** (`employer_share_candidates`, `employer_share_create`): a work item needs a
  shareable confirmation for the record's current version; a certification must be type `certification`, uploaded, with a
  stored file; originals only for selected certifications. The server-side packet builder
  (`lib/server/employer/packet.ts`) applies the same rules and a strict schema, so a forged request is refused twice,
  and the stored packet is re-validated on every read.
- **Supervisor permission.** With the flag on, a supervisor confirming a job sees two unticked boxes: "may be shared with
  employers", and (enabled only after the first) "also show my name, organization and title". Recorded only by that
  reviewer, only for a confirmation, only within 15 minutes of deciding. Without the name permission the employer is
  told the supervisor allowed sharing but did not permit their name to be shown.
- **Customer acknowledgments.** The acknowledgment wording is unchanged (`customer-ack-v1`). With the flag on, the
  confirm form adds a separate, optional, unticked question: "I give the technician permission to share this
  acknowledgment with prospective employers they choose. Employers would see the work description and that a customer
  acknowledged it, but never my name, signature, comments or contact details. If I leave this unticked, my
  acknowledgment is never shared outside QualiTrail." The acknowledgment is recorded either way. Permission is stored
  only if ticked, only through the verified session that confirmed, within 15 minutes. Only acknowledgments with that
  permission are shareable; all others (including every older one) are withheld and counted. Customers are never named.
- **Access.** Accept requires the token and a signed-in account whose confirmed email equals the invited address; the
  technician's own account is refused. Opening creates no profile and no supervisor relationship. An address with a
  pending share may register an account but still cannot create a technician or supervisor profile under the sign-up
  policy. Every API call checks the share's recipient.
- **Originals** (certificates only) open through a 60-second signed URL only if that original was explicitly shared in
  this packet, the share is active (not withdrawn or expired), the caller is the invited account, and the record is still
  the shared version and file. The URL is returned to the caller only and never logged.
  **Limit:** withdrawal, expiry or a change stop any *new* link from being issued immediately, but a signed URL already
  issued is a bearer link to the storage file and keeps working until its own 60 seconds run out (a file already
  downloaded is, of course, out of our control). Each issued link is recorded as `original_opened`.
- **Changes after sharing** are shown as a notice; the packet itself never changes.
- **Technician UI**: a "Share" page (sidebar, flag on only). Nothing is preselected. Per-certificate "also allow the
  original" box; a warning that original certificates may contain personal information appears when any is ticked.
  Mandatory preview with the same component the reviewer sees, a reviewed-it checkbox, then send. The shares list shows
  the masked address, counts, status, views, originals opened, and Withdraw.

## Calls made by the builder (please check)

- Customer permission is a separate checkbox; the acknowledgment wording and version are not changed.
- Share permission and name permission are separate; name requires share.
- Only `certification` records count as certifications; training records are not shareable.
- Technician name and trade are the only profile fields in the packet.
- Supervisor and customer permission can only be given at decision time, not later for older confirmations.
- Masked address hints keep the domain (same as supervisor invitations).
- Default expiry 7 days (choices 3/7/14/30); 10 shares/hour and 20/day per technician.
